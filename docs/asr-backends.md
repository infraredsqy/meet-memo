# meeting · 本地 ASR 后端选型与参数定档

> 这份文档写**两套语音模型为什么是这两套、参数为什么取这个值**。四个配置键（`post.engine` / `post.model` / `post.dtype` / `post.chunk_seconds`）的**当前值**正本在 `docs/service.md`，本文只写依据。
> 量出来的读数（显存峰值、墙钟、实时率）不存档——要新读数就重跑（文末「怎么重量」）；本文只留判据与决定。

## 1. 分工：会中用 GLM-ASR-Nano，会后用 MOSSTD

| 层 | 模型 | 为什么是它 |
|---|---|---|
| 会中 | GLM-ASR-Nano | 10 秒段单段耗时亚秒级，边开会边出字幕晚几百毫秒看不出来 |
| 会后 | `OpenMOSS-Team/MOSS-Transcribe-Diarize`（MOSSTD） | 一次推理同时出转写、说话人编号与时间戳，不必先转写再聚类两套拼；会后时间宽裕（R8） |

两套**不在同一时刻占卡**：会后那条链开跑之前，会中模型先退出显存（见下文「显存交接」）。

## 2. 会后那套的落地形态

- **repo id**：`OpenMOSS-Team/MOSS-Transcribe-Diarize`（`post.model` 的默认值）。
- **版本钉法**：配置键收「HF 仓库 id」或「本地快照绝对路径」两形态，**没有 revision 这一格**；走仓库 id 时解析到的是当时的 `refs/main`，要钉住版本就填本地快照绝对路径。
- **架构一句话**：约 0.9B 的音频 LLM（Whisper-Medium 规格音频编码器 + VQAdaptor + Qwen3 文本解码器），模型卡声明单次推理可吃 90 分钟音频。
- **加载**：远程代码随快照落盘，`trust_remote_code=True`、`dtype="auto"`、`attn_implementation="sdpa"`，与官方 Quickstart 一致。

## 3. 运行时裁决：四条候选

| 候选 | 结论 | 依据 |
|---|---|---|
| **transformers + 官方 helper** | **选它** | 官方参考路径（`trust_remote_code=True`）；上游声明支持的 transformers 区间与项目锁定的版本对得上；远程代码在目标环境跑过多趟推理 0 错误 |
| vLLM | 落选 | 前提是固定版本的 nightly 构建，与本项目「版本逐项锁死」相冲；还要另起常驻服务进程 |
| SGLang Omni | 落选 | 厂商明文排除 CUDA 12 环境（“If you are using a CUDA 12 environment, SGLang is currently not supported”） |
| transcribe.cpp + GGUF | 落选 | 第三方路线，自建运行时、另下权重；量化档在中文会议语料上没有可复现的证据 |

## 4. 精度档与块长

**`post.dtype = bfloat16`**。依据：模型自己的 `config.json` 声明 bf16；官方 helper 在 CUDA 上挑的也是 bf16。**另两档（fp16 / fp32）没有对照证据，不建议改**——官方只发了 bf16 权重，换档会怎样给不出数字。

**`post.chunk_seconds = 450`**。判据一条：**块峰值越过物理显存就落到主机内存换页，墙钟劣化一个量级**。块长要在目标卡上标度（450 / 600 / 900 / 1200 / 1500 秒各跑一趟，量分配峰值与墙钟）：450 秒档在卡内且余量安全，900 秒起越界、1500 秒直接 OOM；换卡要照文末「怎么重量」重标。

**450 是对「默认 `0` = 关闭分块」的有意偏离**：一场正常会议动辄一小时，默认 `0` 会让默认配置踩在越界那一侧。短于 450 秒的音频本来就不切块，小会议的行为与关闭分块一致。

## 5. 显存交接：会后链开跑前把会中模型移出显存

**决定**：两个模型不同时占卡。收尾第 4 步只做「让会中模型退出显存」这一件事，之后那一格停在 `waiting`；会后两条链由按钮或 `meeting post` 另行拉起。暂停 / 继续两个动作接在同一处交接上（暂停放出、继续拉回）。成员语义（`release_gpu()` / `acquire_gpu()`，等在飞推理 5 秒上界、幂等、抛错不拖垮整场）见 `docs/backend-protocols.md`。

**为什么 5 秒上界**：等的是「已加载的模型把当前一段跑完」（正常一段秒级），释放包在这一步自身的预算里——单段超时档 20 秒会把预算整个吃光，自适应收尾预算那档更不行。

**两个已知边界**：① 「打断」与「关停」两格不释放（归管收尾 / 关停的路径）；② 「继续那一刻权重就进显存」做不到——`acquire_gpu()` 交回的是识别器，权重仍由第一段转写时那条加载路径负责。

## 6. 会中防护参数复核

会中那五个防护参数沿用既有标定值：

| 参数 | 标定值 | 默认值 |
|---|---|---|
| 单段硬上限（秒） | 10 | `asr.max_segment_seconds` = 10 |
| 单段识别墙钟硬超时（秒） | 20 | `asr.timeout_seconds` = 20 |
| 单段生成 token 上限 | 400 | `asr.max_new_tokens` = 400 |
| 重复过滤：扫描周期上限（字符） | 40 | `asr.repeat_max_unit` = 40 |
| 重复过滤：覆盖率阈值 | 0.5 | `asr.repeat_min_coverage` = 0.5 |

超时标定（探针实测，不是估计）：10s 段正常识别 3.1–4.2s、30s 段 13–15s → 20s 超时对 10s 段有 ≥5 倍裕量。覆盖率 0.5 的悬崖论证：真循环两行覆盖率 0.995 / 0.993，最高的正常行只有 0.113；命中 2 行、误杀 0 行 → 阈值正好落在悬崖上，不需要精调。

「沿用」的依据：段长默认仍是 10 秒、会中引擎没换，「换 tokenizer 粒度 → 重复判据语义跟着变」的风险不触发。五个值都是热读键。**条件**：将来把段长调离 10 秒，五个值都要按新段长重新标定——30 秒段的探针口径与逐段墙钟不同层，不能直接换算。

## 7. 已知缺口

- 块长与参数标定只覆盖一张卡；换到显存更小的卡要重标，块长对说话人编号数量的代价、实时率也要重测。
- `meeting/offline/segment.py` 在生产路径上是死代码（生产走 runner 里按块长定长硬切的路径，该模块只被测试引用），模块头与现状不符——接回链上或改说法，待定。
- 超时裕量只有「超时 > 段长」一条弱约束，没有「超时 ≥ k 倍实测段耗时」的结构性保证。
- 想加第二个离线后端时缺：引擎注册表、`post.device` / `post.revision` / `post.max_new_tokens` 等键、模型加载不在私有函数里、协议不强制每段带说话人标签。

## 8. 怎么重量

- **验证参数与改动**：`meeting replay <场次目录>` —— 素材截断复制进自己的落地、直调同一条 `run_session`，原目录一个字节不动，跑完打印实时率、逐块耗时与失败分布（详见 `docs/service.md`）。
- **块长标度**：同一段音频按各档秒数各跑一趟，量分配峰值（`torch.cuda.max_memory_allocated`）与墙钟；与整卡占用（`nvidia-smi`）是两种口径，不要混。
