## 会中稿与会后稿怎么用（这一轮的核心）

同一场会的每一路最多有**两份转写**，各自独立、**不合并**，**没有先后、没有谁更可信**：

- **会中稿**（`meeting_transcript_<source>.md`）：时间戳密、连续、延迟低；没有说话人标签；
- **会后稿**（`meeting_offline_transcript_<source>.md`）：整段重跑出来的，每行带聚类编号 `S01`。

**哪几份在手上、各自几行、切了几块，全在上面那份输入清单里逐条写着**：只有会中稿的场次、
只有会后稿的场次都照清单读，缺的那一份不要去找、不要猜。清单里这两份平起平坐：哪一份听得更准，
看的是内容本身。

**对账在生成纪要的流程内部完成**（R12）：不做预先的文本对齐，也不单独产出一份「对账结果」。
两份稿同时读，**按内容判哪一边可信**——会中那份听对了、会后那份听错的地方就采用会中那份，
反过来也一样。某一段两份稿说法冲突时，写出你采信的那一条，并在心里记着另一份说的是什么。

**两份稿的行号空间各算各的**：行号是「那一路那一份稿自己的第几行」。同一段讨论在两份稿上的
行号**不保证对得上**（两份的切行密度不同），别按行号去另一份里找同一句话，要看内容对。
某一路缺了另一份稿时，那一段只读在的那一份；缺哪一份、这一路分不分得出个人，都在上面的
档位说明里写着，照它写附录。

## 质量目标

最终产出 `meeting_final.md` 应该做到：

1. **先结论后细节**：开头就看出这场会定了什么，往下才是分主题的支撑内容；
2. **按主题组织**：核心共识按主题逻辑分组，不按时间顺序罗列；
3. **篇幅跟会议容量匹配**：会开多久、结论有多少，决定纪要写多细；素材里的过程不进终稿；
4. **有判断力**：分得清「团队达成一致的」与「仍有争议的」；
5. **有上下文意识**：这场会跟之前、之后的讨论是什么关系（如果有）；
6. **内部自洽**：被否决的内容不在后面复活，同一个人的立场不自相矛盾，术语统一；
7. **不编造**：没有把握的内容不写，归属不确定就匿名，引号里只放可核对的专有名词；
8. **有温度（可选）**：值得记录的会议花絮留一段。

   主 agent 的上下文里只有阶段状态、文件名与 sub agent 的返回摘要；
2. **sub agent 一次只做一件事**：读 → 分析 → 输出 → 结束，不串任务；
3. **容错**：某个 sub agent 挂了就重新开一个替换，主 agent 不亲自下场做它的工作；
4. **说话人归属**：默认不写谁说的；要点名时用上下文钉死的归属，不确定就匿名，不编造；
5. **最终输出**：`{{SESSION_DIR}}/meeting_final.md`。
